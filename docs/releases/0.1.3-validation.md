# Automatic update detection validation — 2026-10-27

## Finding and fix

A live session-triggered check in 0.1.1 reached GitHub but received HTTP 403:
its shared unauthenticated API quota had no remaining requests. The UI correctly
showed a retry state, but discovery depended on that quota.

Release 0.1.3 replaces API discovery with the public release asset
`https://github.com/butter-computer/del/releases/latest/download/latest.json`.
The packaging script generates the manifest from the DMG and checksum sizes.
All three assets are uploaded before publishing the release. Automatic checks
now have a 60-second cooldown, including retries after failures.

## Live checks without the manual update-check button

Used a locally built public-identity 0.1.2 baseline containing the discovery fix,
then published 0.1.3 while the baseline stayed running.

- Session-opening run: baseline initially showed “Del is up to date”. Invoking
  New session caused “Checking for updates…” followed by “Update to 0.1.3”.
- Independent tab-switch run: temporarily returned 0.1.3 to draft and selected
  0.1.2 as latest, restarted the baseline, and created two empty tabs. Verified
  the startup check completed with “Del is up to date”. Republished 0.1.3 and
  selected it as latest. After the cooldown, Command-1 changed the selected tab
  and started an automatic check. GitHub initially served an older cached latest
  redirect, so that check correctly reported current. Once the public manifest
  resolved to 0.1.3, a subsequent Command-2 tab switch after the cooldown produced
  “Checking for updates…” followed by “Update to 0.1.3”.
- No manual Check click was used in either run. No download/install action was
  needed for these detection tests. The final app was left with the update offer
  visible, and the two empty test tabs were closed.
- The final published latest release is 0.1.3, with all three assets present.

GitHub release propagation/caching can briefly lag publication. Navigation
rechecks after the cooldown and detects the release once the public feed serves
it. The app does not continuously poll or make a request on every rapid tab click.

## Automated isolation of the trigger

The production observer is owned by AppUpdater and watches AppState selection.
Regression tests invoke real AppState session creation and existing-tab selection,
then run the same observer, background check, result delivery, and state transition.
The remote release response and elapsed clock are controlled in these tests.
There is no startup check, window-activation event, or manual check in the fixture.

Tests verify:

- Mere notifications do not fetch a release.
- Session/tab changes inside the cooldown do not fetch.
- Session creation after expiry fetches exactly once and detects the newer release.
- Existing-tab selection after expiry fetches exactly once and detects it.
- A failed check is retried automatically on later session navigation after expiry.
- Subsequent navigation preserves the available-update offer without duplicate work.

Final results:

- App suite: 213 passed, 0 failed, 9 intentionally ignored.
- Workspace suite: 416 passed, 0 failed, 36 intentionally ignored.
- Explicit public release integration: passed using the manifest-hosted discovery
  path and published 0.1.3 DMG, including checksum/signature validation and the
  wrong-version, altered-identity, changed-installation, and binary-tampering cases.

```sh
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
cargo test --locked -p del-app detects_release_without -- --nocapture
cargo test --locked -p del-app session_change_retries_failed_check_after_cooldown
cargo test --locked --workspace
cargo test --locked -p del-app app_updates::tests::public_release_download_and_staging -- --ignored --nocapture
```
